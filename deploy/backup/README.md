# Резервные копии Luna-Sklad

Три скрипта:

- **`backup.sh`** — снимает дамп БД, шифрует, кладёт локально на сервер и
  в Google Drive. Запускается по cron, без участия человека.
- **`restore.sh`** — расшифровывает конкретную копию и восстанавливает её
  в указанную базу данных. Для реального восстановления (авария, перенос).
- **`test-restore.sh`** — то же восстановление, но в одноразовую базу,
  с автоматическим сравнением количества строк по всем таблицам с живой
  БД, и одноразовая база сразу удаляется. Для регулярной проверки, что
  бэкапы реально восстанавливаются, а не просто лежат файлами.

Данные зашифрованы (`age`) всегда и везде за пределами самого процесса
бэкапа — на диске сервера, на Google Drive, в промежуточных файлах. В
открытом виде дамп существует только долю секунды внутри пайпа `pg_dump |
age` при создании копии, и временно на диске при восстановлении (файл
сразу удаляется после `pg_restore`, даже при ошибке — через `trap`).

## 1. Приватный ключ (age) — самое важное

Генерируется **один раз, на своём компьютере, не на сервере**:

```bash
age-keygen -o luna-backup-key.txt
cat luna-backup-key.txt
```

В файле два значения:
- `# public key: age1...` — публичный ключ. Не секрет. Идёт в
  `deploy/backup/.env` на сервере как `AGE_RECIPIENT` — им `backup.sh`
  шифрует копии. Сервер с этим ключом может ТОЛЬКО зашифровать, расшифровать
  им ничего нельзя.
- `AGE-SECRET-KEY-1...` — приватный ключ. Вот этим можно расшифровать
  резервные копии. **Он никогда не копируется на сервер ни в каком виде**,
  включая переменные окружения и файлы — `restore.sh`/`test-restore.sh`
  запрашивают его в терминале каждый раз, когда он нужен, и не сохраняют
  его на диск ни на секунду.

### Где хранить приватный ключ — явная рекомендация

1. **Основное место — менеджер паролей** (1Password, Bitwarden и т.п.),
   отдельной защищённой заметкой. Зашифровано, синхронизируется между
   вашими устройствами, доступно в любой момент, когда понадобится
   восстановление.
2. **Дополнительно — одна полностью offline-копия** на случай, если
   аккаунт менеджера паролей станет недоступен (забыли мастер-пароль,
   блокировка аккаунта, недоступность сервиса): распечатать на бумаге и
   положить в сейф/надёжное место, или сохранить на отдельную флешку,
   которая физически хранится не рядом с сервером.

**Если этот ключ потерян — все резервные копии навсегда нерасшифровываемы.**
Это не ошибка дизайна, а то, как работает шифрование — специально нет
"восстановления пароля". Отсюда и двойная рекомендация выше: один удобный
источник на каждый день, один надёжный — на случай катастрофы с первым.

## 2. Google Drive через rclone (service account — без браузера на сервере)

Рекомендуемый способ для сервера, который работает без присмотра: service
account, без интерактивного OAuth через браузер (ему не грозит протухание
токена, в отличие от обычного личного входа).

1. **Google Cloud Console** (console.cloud.google.com) → создать проект
   (или использовать существующий) → включить **Google Drive API**
   (APIs & Services → Library → найти "Google Drive API" → Enable).
2. **IAM & Admin → Service Accounts → Create Service Account.** Имя —
   любое, например `luna-backup`. Роли на проект — не нужны (доступ к
   файлам даётся не через IAM, а через обычный "поделиться" в Google Drive,
   см. ниже).
3. У созданного service account → **Keys → Add Key → Create new key →
   JSON.** Скачается файл вида `project-id-xxxxx.json` — в нём есть поле
   `client_email` (что-то вроде
   `luna-backup@project-id.iam.gserviceaccount.com`) — он понадобится на
   следующем шаге.
4. Загрузите этот JSON-файл на сервер (например, `scp`) в
   `/etc/luna-backup/gdrive-service-account.json`, права `600`, владелец —
   `deploy`:
   ```bash
   sudo mkdir -p /etc/luna-backup
   sudo mv gdrive-service-account.json /etc/luna-backup/
   sudo chown deploy:deploy /etc/luna-backup/gdrive-service-account.json
   sudo chmod 600 /etc/luna-backup/gdrive-service-account.json
   ```
5. В своём обычном Google Drive (личном или рабочем) создайте папку,
   например `luna-backups`, и **поделитесь** ею с email service account'а
   из шага 3 (как с обычным пользователем, права "Редактор"). Важно именно
   так — у service account нет собственной квоты на обычном (не Workspace)
   Google Drive, но файлы, которые он пишет в папку, которой с ним
   поделились, считаются в квоту **вашего** аккаунта, а не его — поэтому
   шаг с "поделиться" обязателен, не пропускайте его.
6. Откройте эту папку в браузере и возьмите её ID из адресной строки:
   `https://drive.google.com/drive/folders/`**`ВОТ_ЭТО_ID`**.
7. На сервере — `~/.config/rclone/rclone.conf` (создать, если нет):
   ```ini
   [gdrive]
   type = drive
   service_account_file = /etc/luna-backup/gdrive-service-account.json
   root_folder_id = ВОТ_ЭТО_ID
   ```
8. Проверка:
   ```bash
   rclone lsd gdrive:
   rclone mkdir gdrive:daily
   rclone mkdir gdrive:monthly
   ```
   Если выдаёт ошибку про квоту (`storageQuotaExceeded`) — значит папку не
   расшарили на service account (шаг 5) или `root_folder_id` указывает не
   туда.

`RCLONE_REMOTE=gdrive` и `RCLONE_FOLDER=` (пустая строка, раз
`root_folder_id` уже указывает прямо на нужную папку) — пропишите в
`deploy/backup/.env`. Если вместо `root_folder_id` используете путь
(`RCLONE_FOLDER=luna-backups` без `root_folder_id`) — тоже сработает, но
`root_folder_id` надёжнее: без неоднозначности, если когда-то появится
вторая папка с таким же именем.

## 3. Настройка

```bash
cp deploy/backup/.env.example deploy/backup/.env
nano deploy/backup/.env   # DATABASE_URL, AGE_RECIPIENT, RCLONE_*, TELEGRAM_*
```

Нужны установленные на сервере: `age`, `rclone`, `postgresql-client`
(для `pg_dump`/`pg_restore`/`psql`, версия клиента — не ниже версии
Postgres на сервере, сейчас 18):

```bash
sudo apt-get install -y age rclone postgresql-client-18
```

## 4. Расписание

См. `crontab.example` — ежедневно в 03:00 всегда, и каждые 3 часа **только
в дни ярмарки** (включается/выключается файлом-меткой, без правок cron):

```bash
# перед ярмаркой
touch /opt/luna/backups/.fair-active
# после
rm /opt/luna/backups/.fair-active
```

## 5. Хранение (retention)

- Локально на сервере: `RETENTION_LOCAL_DAYS` (по умолчанию 7 дней) —
  старше просто удаляются `backup.sh`'ом на каждом запуске.
- Google Drive, `daily/`: `RETENTION_DRIVE_DAILY` (по умолчанию 30) —
  последние N копий, лишние удаляются автоматически.
- Google Drive, `monthly/`: `RETENTION_DRIVE_MONTHLY` (по умолчанию 12) —
  первая копия каждого месяца, тоже автообрезка.

## 6. Уведомления в Telegram

`TELEGRAM_BOT_TOKEN` + `TELEGRAM_ADMIN_CHAT_ID` в `.env` — тот же бот и
chat_id, что уже настроены для приложения. Сообщение приходит **только при
ошибке** (самого бэкапа или проверки восстановлением) — успешные запуски
не шумят в чат, смотрите их в `/var/log/luna-backup.log`.

## 7. Проверка восстановлением — `test-restore.sh`

> Бэкап, который никогда не восстанавливали — это не бэкап.

```bash
deploy/backup/test-restore.sh                       # берёт самую свежую локальную копию
deploy/backup/test-restore.sh /путь/к/конкретной.dump.age
deploy/backup/test-restore.sh daily/luna-20260101T030000Z.dump.age   # скачает с Drive
```

Скрипт спросит приватный ключ в терминале, восстановит копию в одноразовую
базу `luna_test_restore_<время>`, сравнит количество строк по каждой
таблице с живой БД, выведет таблицу `ТАБЛИЦА / ЖИВАЯ БД / ВОССТАНОВЛЕНО /
СТАТУС` и **сам удалит** одноразовую базу в конце — успешно или с ошибкой,
не важно.

**Запускать руками регулярно** (раз в одну-две недели достаточно) — именно
потому что нужен приватный ключ, автоматически по cron без человека это не
делается (см. `crontab.example`, там это явно объяснено). Да, это ручная
операция, но и 5 минут раз в пару недель — вменяемая цена за уверенность,
что бэкапы реально работают, а не просто существуют файлами на диске.

## 8. Восстановление по-настоящему (авария/перенос) — `restore.sh`

```bash
deploy/backup/restore.sh /путь/к/файлу.dump.age имя_целевой_базы
deploy/backup/restore.sh daily/luna-20260101T030000Z.dump.age имя_целевой_базы   # с Drive
```

**Целевая база данных будет удалена и создана заново** — никогда не
указывайте имя боевой БД, если не собираетесь её полностью перезаписать.
Для безопасного восстановления: восстановите во ВРЕМЕННОЕ имя, проверьте
данные, и только потом вручную переключите приложение (`DATABASE_URL`) на
восстановленную копию — так остаётся путь назад, если что-то не так.
