# Перенос Luna-Sklad на свой VPS — Фаза 4: настройка сервера

Эта папка — скрипты для первоначальной настройки чистого Ubuntu 24.04 VPS
под Luna-Sklad. Всё здесь рассчитано на то, что вы заходите на сервер по
SSH и запускаете команды сами, шаг за шагом — ничего не выполняется
автоматически.

Что уже сделано в этой фазе и что ещё нет:
- ✅ Настройка самого сервера (пользователь, SSH, firewall, Docker)
- ✅ Nginx как reverse-proxy + Let's Encrypt
- ⏳ Резервные копии в Google Drive — Фаза 5
- ⏳ Перенос базы данных с Render — Фаза 6
- ⏳ Автодеплой через GitHub Actions — Фаза 7

Пока ничего из этого не переносит сам сайт с Render — после Фазы 4 у вас
просто готовый, настроенный сервер, на котором ещё нет самого приложения.

## Что вам понадобится до начала

- Свежий VPS с Ubuntu 24.04, root-доступ по SSH (обычно присылает хостер
  на почту вместе с IP-адресом).
- Ваш SSH-ключ (если на вашем компьютере его ещё нет — `ssh-keygen -t
  ed25519`, затем `ssh-copy-id root@<ip>` перед началом, либо просто
  вставите ключ вручную на шаге 1).
- Домен, у которого вы можете поменять DNS-записи (для Let's Encrypt).
  Пока не обязателен для шагов 1-2, но нужен для шага 3 (выпуск
  сертификата) — лучше сразу направить `A`-запись домена на IP сервера,
  DNS обновляется не мгновенно.

## Шаг 1 — настройка сервера: `setup-server.sh`

Делает: пользователь `deploy` (sudo, без пароля — только по ключу),
отключает вход по паролю и под root, ставит `fail2ban` и
`unattended-upgrades`, создаёт 2GB swap, ставит Docker + Compose plugin,
настраивает `ufw` (только 22/80/443).

```bash
ssh root@<ip-сервера>
curl -fsSL -o setup-server.sh https://raw.githubusercontent.com/bxbyarchi/luna/main/deploy/setup-server.sh
bash setup-server.sh
```

Если скрипт не найдёт ваш ключ в `/root/.ssh/authorized_keys` — он сам
попросит вставить публичный ключ (`id_ed25519.pub`/`id_rsa.pub`) прямо в
терминал.

**Критически важно**: после завершения скрипта **не закрывайте** текущую
root-сессию. Откройте **новый** терминал и проверьте, что вход как
`deploy` работает:

```bash
ssh deploy@<ip-сервера>
```

Если не зашло — у вас всё ещё открыта root-сессия, в которой можно
разобраться и починить. Если закрыть её раньше, не проверив — можно
остаться без доступа к серверу вообще (вход под root и по паролю скрипт
уже отключил).

Дальше все команды — **от `deploy`-пользователя**, через `sudo`.

## Шаг 1.5 — клонировать репозиторий

Шагам 2 и 3 нужны не только сами скрипты, но и их шаблоны/сниппеты рядом
(`nginx/templates/`, `nginx/snippets/`) — поэтому дальше работаем уже из
клона репозитория, а не через одиночный `curl`, как в Шаге 1:

```bash
# от deploy-пользователя
git clone https://github.com/bxbyarchi/luna.git ~/luna
cd ~/luna
```

Эта же папка `~/luna` дальше понадобится и в Фазе 6 (сама база с
`docker-compose.yml`), и в Фазе 7 (автодеплой через `git pull` в ней же) —
клонируете её один раз, остальные фазы просто этой папкой и пользуются.

## Шаг 2 — Nginx: `nginx/install-nginx.sh`

Ставит Nginx и Certbot, общие настройки (gzip, security-заголовки),
убирает дефолтную заглушку-приветствие.

```bash
sudo bash deploy/nginx/install-nginx.sh
```

## Шаг 3 — сайт для конкретного домена: `nginx/add-site.sh`

Создаёт reverse-proxy на 127.0.0.1:<порт> для домена и выпускает
Let's Encrypt сертификат. Один и тот же скрипт годится для Luna-Sklad и
для любых будущих приложений на этом же сервере — просто другой
домен/порт.

```bash
# Luna-Sklad — порт 3000, как указано в docker-compose.yml
sudo bash deploy/nginx/add-site.sh luna.ваш-домен.ru 3000 ваша-почта@example.com

# Если позже добавите второе приложение на тот же сервер:
sudo bash deploy/nginx/add-site.sh crm.ваш-домен.ru 3001 ваша-почта@example.com
```

Скрипт спросит, настроен ли уже DNS на этот сервер — Let's Encrypt
проверяет владение доменом по HTTP, без правильного DNS сертификат не
выпустится. Если DNS ещё не готов — ответьте "N", сайт будет работать по
обычному HTTP, а когда DNS подтянется — запустите скрипт ещё раз (или
`sudo certbot --nginx -d ваш-домен.ru`).

Автопродление сертификата уже настроено самим пакетом `certbot` (через
systemd-таймер) — отдельно ничего делать не нужно. Проверить можно так:

```bash
sudo certbot renew --dry-run
```

## Важно про Docker и firewall

Docker управляет `iptables` напрямую и для **опубликованных портов**
контейнеров обходит правила `ufw` — т.е. если в `docker-compose.yml`
у сервиса стоит `ports: - "0.0.0.0:5432:5432"`, `ufw` его не заблокирует,
даже если такого правила в `ufw` нет.

В `docker-compose.yml` (сделано в Фазе 3) это уже учтено:
- У Postgres секции `ports:` нет вообще — он недостижим снаружи.
- Приложение опубликовано на `127.0.0.1:3000`, не на `0.0.0.0:3000`.

Если в будущем добавляете сервис в `docker-compose.yml` — **всегда**
`127.0.0.1:<порт>:<порт>`, никогда просто `<порт>:<порт>`.

## Проверка после всех шагов

```bash
# DNS и сертификат
curl -I https://luna.ваш-домен.ru/

# nginx отдаёт правильные заголовки
curl -I https://luna.ваш-домен.ru/ | grep -i "x-frame\|strict-transport"
```

Само приложение на этом сервере пока не запущено (`docker compose up` —
дело Фазы 6, когда будет перенесена база данных) — в Шаге 3 nginx
проксирует на порт 3000, где пока ничего не слушает, это нормально до
переноса.
