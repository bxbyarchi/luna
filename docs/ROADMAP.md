## 1. Главная идея

Единая система управления складами, товарами, перемещениями, сотрудниками, а в
дальнейшем — ярмарками и кассами.

Архитектура обязана выдержать рост с 5 площадок до 30–40 домиков и касс **без
переписывания**. Поэтому сущности разделены принципиально:

```
склады ≠ площадки ≠ домики ≠ кассы ≠ сотрудники ≠ продажи
```

## 2. Структура складов

### Центральный склад

**Бишкек — центральный.** Туда приходит всё новое:

```
Покупка → Центральный склад Бишкек → распределение по объектам
```

Из него товар передаётся на: Площадь, Азия Молл, Скай Парк, Кой Таш.

- **Лермонтова** — реквизит, техника, оборудование.
- **Прохладное** — домики и оборудование ярмарки.

## 3. Логика движения товара

```
Закупка → Бишкек-центральный → Перемещение → Локальный склад
        → Объект / домик → Продажа / использование → Отчётность
```

**Ключевое правило:** центральный склад не уменьшается от того, что кто-то где-то
продал товар. Он уменьшается только при подтверждённом перемещении.

Отдельный контур:

```
ОШ
├── свой склад
├── свои закупки
└── свои остатки
```

## 4. Роли и права

| Роль | Код | Ранг | Доступ |
|------|-----|------|--------|
| Завхоз / главный администратор | `admin` | 4 | всё, все склады |
| Управляющий | `manager` | 3 | без отчётов, аудита, настроек |
| Бухгалтер | `accountant` | 2 | + списания, без категорий и сотрудников |
| Сотрудник склада | `warehouse` | 1 | только свой склад |

Иерархия — `artifacts/api-server/src/middleware/rbac.ts`.
Разграничение по складу — `artifacts/api-server/src/lib/warehouseScope.ts`.

Сотрудник Азия Молл не должен видеть внутреннюю информацию Оша или центрального склада.

## 5. Модули системы

### Приход товара
`Поступление → выбор склада → товар → количество`
Пример: купили 100 стульев → Бишкек-центральный → +100.

### Перемещения (двухэтапные)
1. Завхоз создаёт перемещение;
2. товар списывается с источника в той же транзакции;
3. статус `pending`;
4. склад-получатель принимает (`accept`) или отклоняет (`reject`);
5. только после подтверждения товар появляется на складе назначения;
6. при отклонении остаток возвращается на склад-источник;
7. в истории: кто создал, кто принял, откуда, куда, какой товар, количество, даты.

### Товары и категории
Категории → товары → единицы измерения → остатки → складские остатки → история движения.
Примеры: *Мебель* (стол, стул, диван), *Реквизит* (декорация, костюм, свет).

### Списание
`Списание → склад → товар → количество → причина → подтверждение`
Причины: повреждение, поломка, потеря, расход, утилизация, другое.

### Инвентаризация
Фактический пересчёт по конкретному складу:
```
По системе: 50 / Фактически: 47 / Разница: −3
```
После подтверждения — сохранение истории.

### Аренда
Выдача и возврат вещей и оборудования: кому, сколько, до какой даты, статус.

### Сотрудники
Имя, email, роль, склад, статус, Telegram, история действий.
Завхоз назначает сотруднику конкретный склад.

### Журнал аудита
Система должна отвечать на вопрос «кто что сделал»:
```
Арсен · 21.09.2026 18:43 · создал перемещение · Бишкек → Азия Молл · Стулья × 20
```
Нужно, чтобы нельзя было сказать «я этого не делал».

### Отчёты и аналитика
- **по складам:** остатки, движение, приход, расход, списания;
- **по товарам:** купили / переместили / списали / осталось;
- **по сотрудникам:** кто какие операции выполнял;
- **по периодам:** день, неделя, месяц, произвольный период.

## 6. Ярмарка «Северное сияние» — отдельный уровень

**5 площадок × 6–8 домиков = 30–40 домиков.**

Кассы — отдельный слой, а не ещё один склад:

```
Площадка → Домик → Касса → Кассир → Смена → Продажи → Отчёт
```

### Кассовая система
Открытие смены → кассир → товары → количество → цена → скидка → итог →
наличные/безнал → закрытие смены → возвраты → отчёт.
Завхоз/администратор видит всю картину.

### Связь склада и ярмарки

```
             ЦЕНТРАЛЬНЫЙ СКЛАД
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
      Площадка    Азия     Скай Парк
          │
       Домики
          │
       Кассы
          │
      Продажи
          │
       Отчёты
```

## ✅ Причина 500-х найдена и устранена (22.09.2026)

Воспроизведено локально: поднят PostgreSQL 16, применены миграции, запущен
собранный сервер ровно теми же командами, что у Render. Причин оказалось три,
и они накладывались друг на друга.

### 1. На Render не заданы ключи Clerk — это и есть источник 500-х

`clerkMiddleware()` монтируется глобально, до роутера `/api`. Без
`CLERK_SECRET_KEY` он выбрасывает `Missing Clerk Secret Key` на **каждом**
запросе, поэтому 500 отдавал даже `/api/healthz`, который вообще не требует
авторизации.

Ключи жили в `.replit`, в секции `[userenv.shared]`, а Render этот файл не
читает. В `render.yaml` были объявлены только `DATABASE_URL` и `NODE_ENV`.

Замер до и после (локально, на чистой базе):

| Запрос | Без ключей Clerk | С ключами |
|--------|------------------|-----------|
| `/api/healthz` | 500 | **200** |
| `/api/locations` | 500 | **401** |
| `/api/transfers` | 500 | **401** |
| `/api/auth/me` | 500 | **401** |

401 — правильный ответ: маршрут работает и просит авторизацию.

**Сделано:** в `render.yaml` объявлены `CLERK_SECRET_KEY`,
`CLERK_PUBLISHABLE_KEY`, `CLERK_JWT_KEY` и `VITE_CLERK_PUBLISHABLE_KEY` со
`sync: false` — значения задаются в дашборде Render, в репозиторий не попадают.
Добавлен `healthCheckPath: /api/healthz`.

> `VITE_CLERK_PUBLISHABLE_KEY` нужен **во время сборки**: Vite вшивает
> `VITE_*` в бандл. Без него фронтенд падает при загрузке — белый экран.

### 2. Сборка на Render падала целиком

`pnpm run build` = `pnpm run typecheck && ...`, а typecheck не проходил:
14 ошибок в формах фронтенда. По той же причине был красный CI на GitHub.

Причина: `@hookform/resolvers@3.10.0` объявляет пиром только `react-hook-form`,
но не `zod`. pnpm не кладёт zod рядом с пакетом, и TypeScript берёт zod из
скрытого hoist-каталога `node_modules/.pnpm/node_modules/` — а там **zod 4.3.6**
(его тянет `@scalar/openapi-types`). Приложение же использует zod 3.25.76.
Отсюда `ZodObject` (v3) против `ZodType<…, $ZodTypeInternals<…>>` (v4).

**Сделано:** в `pnpm-workspace.yaml` добавлен `packageExtensions`, объявляющий
`zod` пиром `@hookform/resolvers`. Теперь рядом с резолвером линкуется
zod 3.25.76 — та же версия, что у кода. Typecheck и полная сборка проходят.

### 3. `prestart` мог зависнуть, а миграции отставали от схемы

Было: `prestart: pnpm --filter @workspace/db push`. `drizzle-kit push`
переходит в интерактивный вопрос на изменениях, которые считает
разрушительными, — на Render это зависание или падение деплоя.

Вдобавок папка миграций отставала: в ней было 11 таблиц, а в схеме 14.
Не хватало ровно складской части — `locations`, `warehouse_stock`,
`warehouse_transfers` — плюс колонок `location_id` в четырёх таблицах.

**Сделано:**
- сгенерирована миграция `0002_bumpy_raza.sql` — чисто аддитивная, без `DROP`;
- `prestart` переведён на `drizzle-kit migrate`: неинтерактивно, по журналу,
  идемпотентно;
- добавлены скрипты `generate`, `migrate`, `baseline`.

Проверено на живой базе: с нуля создаются все 14 таблиц, второй запуск —
чистый no-op с кодом 0 (то есть рестарты Render безопасны).

#### Разовый baseline, если база уже создана старым `push`

Если в `luna-db` таблицы уже есть, но журнала `drizzle.__drizzle_migrations`
нет, `migrate` упадёт с `relation already exists` (проверено). Лечится один раз:

```bash
DATABASE_URL=... pnpm --filter @workspace/db baseline        # пробный прогон
DATABASE_URL=... pnpm --filter @workspace/db baseline --yes  # запись
DATABASE_URL=... pnpm --filter @workspace/db migrate
```

Скрипт помечает существующие миграции применёнными, не трогая схему. Запускать
только если схема в базе соответствует последней миграции.
